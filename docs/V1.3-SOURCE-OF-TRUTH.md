# Claw Scrapper — Source of Truth V1.3

**Status:** Authoritative V1.3 architecture.
**Scope:** Discovery, free/manual SERP harvesting, Premium SERP Extraction, crawling, extraction, validation, qualification, deduplication, and CSV/Excel/Google Sheets exports.
**CRM:** Out of scope.

## 1. Core principle

Claw Scrapper is a commercial lead-research system optimized for lead recall.
Search engines are discovery surfaces with two supported acquisition modes. Free Manual SERP Discovery uses Scrappee-generated Google/Bing parameters and the user's normal browser. Premium SERP Extraction accepts a pasted Google/Bing search URL and uses a paid SERP provider to retrieve the SERP without requiring the user to operate the search page. Both modes load SERP result occurrences into the authenticated user's Current Scrap; Scrapy autonomously crawls those URLs.

**Hard rule:** do not solve, bypass, evade, or fight Google/Bing CAPTCHA. If a challenge appears, the user handles it in the real browser.

## 3. Scrappee UI

The customer-facing application is Scrappee. CLI is development/test only.

### 3.1 Current Scrap is the primary working workspace

The Current Scrap page is the user's active workspace for SERP acquisition and submission. It must make the current Scrap, collected state, next action, and completion action immediately understandable. Technical counters remain available but are secondary to the workflow.

The Current Scrap page contains two SERP acquisition panels on the same page:
- **Manual SERP Discovery (Free):** generated Google/Bing search suggestions. The user opens the real SERP in the normal browser, handles any CAPTCHA/challenge manually, and uses the browser extension to capture rendered result cards.
- **Premium SERP Extraction ($1 per extraction by default):** the user pastes a Google or Bing search URL. The backend sends the request to a configured paid SERP provider and loads the result occurrences directly into the authenticated user's Current Scrap.

The Premium SERP Extraction price is administrator-configurable and must not be hard-coded.

### 3.2 Current Scrap state is database-backed

PostgreSQL is the source of truth for Current Scrap state and displayed acquisition counts. Browser-local state, extension state, process-local dictionaries, or cached UI state must not be authoritative.

After a successful SERP capture/import, the persisted state must be reflected in Scrappee without requiring logout/login. At minimum the UI must correctly reflect:
- SERP result occurrences captured;
- SERP capacity used / configured limit;
- URL occurrences;
- leads when downstream processing has produced them; and
- Scrap status.

The same state must remain visible after page reload, logout/login, session timeout, or browser restart. A successful extension capture such as 30 captured results must not leave Current Scrap displaying zero persisted results.

### 3.3 Manual SERP controls

Manual search suggestions must display the complete generated query. Provider names must remain readable as **Google** or **Bing** and long queries must wrap or otherwise remain fully accessible. Copying a query must copy the complete query.

The redundant **ADD** control is removed. Generated search suggestions do not require a separate add/selection step before opening them.

The ambiguous **Open** control is replaced with explicit provider-specific actions:
- **Open in Google**
- **Open in Bing**

These actions open the generated search in the user's normal browser. They do not remotely operate Google/Bing and do not perform CAPTCHA solving or bypassing.

The manual workflow must be explicit in the UI:
1. Choose a generated search.
2. Open it in Google or Bing.
3. Browse the rendered result pages as needed.
4. The browser extension captures result cards and synchronizes them to the Current Scrap.
5. Return to Scrappee and review the collected state.
6. When finished, click **URL SUBMISSION COMPLETED**.

No blank, clipped, or unexplained controls are acceptable. Every visible action control must have a clear purpose.

### 3.4 Current Scrap lifecycle and completion action

The active Scrap remains the user's Current Scrap until the user explicitly clicks **URL SUBMISSION COMPLETED**. Logout, session timeout, browser restart, re-login, or page reload must not clear or implicitly complete it.

While a Scrap is active, the UI must clearly communicate that the user is working on that Scrap and that another Scrap cannot become active until URL submission is completed.

**URL SUBMISSION COMPLETED** is the explicit transition from the acquisition workspace into the submitted/processing lifecycle. Once submitted, the Current Scrap lock is released and the user may create another Scrap subject to wallet balance and configured commercial limits.

### 3.5 Current Scrap information hierarchy

The UI must prioritize the user's workflow over technical telemetry. The primary presentation is:

```text
Current Scrap
  ↓
Search suggestions / acquisition actions
  ↓
SERP collection counts and collected results
  ↓
URL SUBMISSION COMPLETED
  ↓
Live processing status
  ↓
Leads / Results / Exports
```

The counters **SERP results**, **SERP capacity**, **URL occurrences**, **Leads**, and **Status** may remain visible, but they are secondary and must not obscure the primary actions.

### 3.6 UI acceptance criteria

1. Capturing SERP results through the extension causes the persisted Current Scrap counts to update.
2. Captured results remain visible after reload and re-authentication.
3. Current Scrap state is isolated per authenticated user.
4. A user cannot create a second active Scrap while the current Scrap remains active.
5. The ADD control is absent from Manual SERP Discovery.
6. Google/Bing opening controls explicitly identify their destination.
7. Generated search queries are fully readable and copyable.
8. The manual workflow is understandable without guessing what each control does.
9. **URL SUBMISSION COMPLETED** is clearly visible and is the explicit completion action.
10. Completing URL submission releases the Current Scrap lock and permits creation of the next Scrap.
11. No logout, timeout, reload, or browser restart clears an active Scrap.
12. UI telemetry observes persisted job state and does not alter pipeline decisions.

Premium extraction is a paid alternative to manual browser harvesting. It is not a remote browser, does not depend on the user solving CAPTCHA, and must not implement CAPTCHA solving or bypassing. The paid provider is responsible for its own search-engine access, proxy/anti-bot infrastructure, and provider-specific retrieval mechanisms.

Both acquisition modes feed the same downstream pipeline:
SERP result occurrences → URL validity checks → URL occurrence deduplication → Scrapy → bounded crawl → evidence → extraction/validation → qualification → lead deduplication → exports.

Premium extraction is scoped to the authenticated user's Current Scrap and must never place results in another user's Scrap.

## 4. Query Strategy Engine

The previous keyword-permutation model is replaced by strategic query generation.

Strategies may combine:
- exact target phrases
- role terminology and synonyms
- product/object
- industry
- geography
- organization/employer
- contact evidence terms
- source/network restrictions
- Boolean operators
- negative operators
- provider-specific search syntax

The engine generates strategically diverse parameters rather than blindly permuting keywords.

The search strategy is universal; the actual syntax is provider-specific.
## 5. Google and Bing adapters

Google and Bing are the active V1.3 search providers. DuckDuckGo is not active.

The free/manual adapters generate search URLs but do not autonomously scrape Google/Bing from the backend.

Premium SERP Extraction is a separate paid acquisition path. It accepts a user-supplied Google/Bing search URL and calls a configured third-party SERP provider through a provider adapter. The provider returns normalized SERP results; the backend never operates a search-engine browser and never solves or bypasses CAPTCHA.

The provider layer must be abstracted so the application is not coupled to one vendor. A first provider may be selected during implementation, but provider choice is an implementation/configuration decision and not a permanent architectural dependency.

Confirmed working examples from manual testing:

Google:
```text
+"gold buyer" +"india" +"email" +site:linkedin.com/in/
```

Bing:
```text
"buyer" "india" -intitle:"profiles" -inurl:"dir/" site:in.linkedin.com/in/
```

These are provider-specific examples, not permanent templates.

## 6. User-browser discovery handoff

Scrappee does not run a remote browser for Google/Bing discovery. Search-engine interaction happens in the user's normal browser so the user's own browser profile, network, cookies, and challenge handling remain in control.

The Scrappee Browser Import extension is the supported handoff mechanism. It uses Chrome's user-invoked `activeTab` access and scripting to inspect the current rendered SERP only when the user clicks the extension action.

Responsibilities:
- generate provider-specific search parameters
- open Google/Bing search URLs in the user's normal browser
- allow the user to navigate and handle CAPTCHA/challenges normally
- extract destination URLs from the rendered SERP after explicit user invocation
- return URL occurrences and SERP result evidence to the authenticated user’s Current Scrap

The extension does not automate Google/Bing, solve CAPTCHA, bypass challenges, or operate a server-side browser.

## 7. SERP harvesting

Scrappee extracts actual destination URLs from SERP results, not Google/Bing tracking/search URLs.

Manual harvesting reads the rendered SERP in the user's normal browser through the extension. The user controls pagination and challenge handling.

Premium SERP Extraction reads the pasted Google/Bing search URL through the configured paid SERP provider. Provider pagination/depth is controlled by the configured premium extraction limits and the per-Scrap SERP capacity. The provider response is normalized into the same SERP result occurrence model used by manual harvesting.

A selected/manual SERP or premium extraction can therefore produce many destination URL occurrences. Premium extraction does not require the user to open the search URL in a browser and does not rely on the user's browser CAPTCHA state.

## 8. URL policy

**Exact URL occurrence deduplication is required.**

Repeated captures of the same normalized destination URL within the same Scrap must not
create repeated crawl submissions. The first occurrence remains authoritative for crawl
submission; provenance may retain occurrence metadata as designed. Domain-level collapsing
is not permitted because different destination paths are independent targets.

Example:
```text
Query A → https://example.com/team/john
Query B → https://example.com/team/john
Query C → https://example.com/team/john
```

All occurrences remain crawl inputs.

Different paths are independent targets. URL validity checks remain separate from deduplication.

Crawler URL limits bound the number of URL occurrences submitted/processed.
## 9. Scrapy

Scrapy is the primary autonomous crawler after SERP URL collection.

It handles scheduling, concurrency, HTTP downloading, retries, redirects, robots, throttling, response processing, documents, Playwright escalation where required, and bounded internal-link expansion.

All supplied URL occurrences are crawl inputs subject to configured limits. Scrapy does not use a lead-quality priority scorer.

Relevant same-domain navigation signals include contact, team, staff, people, management, directory, procurement, purchasing, sales, buyer, buyers, leadership, and about-us. These are navigation controls, not lead scoring.

## 9A. Document Acquisition and Extraction

Scrapy acquires documents discovered from valid SERP seed URLs and bounded same-domain expansion. Parsing is downstream extraction.

### 9A.1 Acquisition contract

- Scrapy downloads document responses as raw bytes and retains URL and response metadata, including content type and HTTP status.
- Documents are subject to configured crawl URL/page, exhaustion, and other operational limits.
- No second crawler is used for documents.
- OpenClaw is not the document acquisition or parsing engine.
- A document parsing failure must not terminate the crawl; it is recorded as bounded diagnostic/evidence state and collection continues.

### 9A.2 Supported document parsing

After acquisition, format detection uses mature format-specific libraries rather than a custom parser:

| Format | Parser |
|---|---|
| PDF | `pypdf` |
| DOCX | `python-docx` |
| CSV | `pandas` |
| XLS/XLSX | `pandas` |

Legacy binary `.DOC` is unsupported in V1.3.

### 9A.3 Normalization and downstream processing

Parsed content is normalized into the same evidence/content representation used by HTML collection and enters the existing downstream pipeline:

`document bytes → format parser → normalized text/evidence → deterministic extraction → LLM when necessary → Pydantic Lead validation → qualification → lead deduplication → export`

Partial contact evidence remains valid research input. Missing Lead fields may be enriched from other related pages or documents collected by the bounded crawl.

Document parsing is an extraction concern, not a crawling concern: Scrapy acquires and bounds the crawl; mature parsers interpret document bytes; the existing evidence, validation, qualification, deduplication, and export stages remain unchanged.

## 10. Evidence and extraction

Deterministic-first order:
JSON-LD/Schema → structured HTML → metadata → email → phone → visible text → LLM research/extraction when necessary.

A page containing only an email is still useful evidence. Missing fields may be enriched from related crawled pages/documents.

## 11. Lead acceptance

**A personal email is optional and is not sufficient by itself to accept a Lead.**

The exact individual-lead acceptance contract is:

```text
(first_name OR last_name)
AND
at least ONE of:
position, company_name, phone, city, state, country, website
```

If email is present, it must be personal. Email-only, company-only, and name-only records
are rejected. Supporting evidence must be a real person-specific field; extraction artifacts
such as email-list/database titles, email addresses misclassified as positions, or
URL/domain fragments are not valid supporting evidence.

No fixed provider/domain allowlist exists. Personal-email classification is based on mailbox semantics, not domain provider.

## 12. Client domain rules

Domain filtering is controlled by a persistent **per-user/client domain rules table** managed from the authenticated Scrappee UI. Each rule contains a normalized domain and a rule type: `blacklist` or `whitelist`.

Clients can add, remove, and view their own domain rules. Rules are isolated to the authenticated client and never affect another client.

Domain matching is normalized before evaluation: lowercase, protocol removed, and `www.` normalized away. Domain rules apply to the extracted source/lead domain and do not introduce URL deduplication.

Rule behavior:
- **Blacklist:** matching domains are rejected and cannot produce/export Leads.
- **Whitelist:** matching domains are explicitly allowed to proceed through normal extraction and qualification.
- **No rule:** normal V1.3 extraction and qualification rules apply.
- **Conflict:** blacklist takes precedence over whitelist.

Whitelist is not a replacement for Lead qualification. A whitelisted domain still must satisfy the normal V1.3 Lead acceptance rules. Provider/domain is not otherwise used as a fixed acceptance allowlist.

The Settings area must provide a **Domain Rules** manager with domain, rule type, add, remove, and view operations.

## 12. Pydantic and self-correction

Pydantic is the validation safety boundary. Invalid candidates cannot be exported as Leads.

Validation failure may enter a bounded research/correction loop:
```text
Extract → Validate → Correct/Research → Re-extract → Validate → terminate
```

No infinite LLM retry cycle.

## 13. Qualification and lead deduplication

Discovery and qualification are separate.

Discovery finds search-result sources and URL occurrences. Qualification determines whether extracted evidence satisfies Lead acceptance.

URL occurrence deduplication occurs before crawl submission within each Scrap. Lead deduplication remains downstream after extraction, validation, and qualification. URL occurrence/provenance must remain available independently of final lead deduplication.
## 14. Configurable controls

Operational controls remain centralized and configurable:
- maximum generated search parameters
- provider failure limits where applicable
- URL validity checks
- maximum crawl pages
- maximum crawl URL occurrences
- pagination limits
- duplicate/exhaustion/no-progress stopping controls

Search-parameter budget, harvested URL count, crawled page count, and final lead count are independent quantities.

## 15. ReAct control loop

Autonomous operational logic retains:
```text
Observe → Evaluate → Choose → Execute → Observe
```

This governs crawling, extraction, enrichment, validation, and bounded recovery. It does not decide whether a human-selected Google/Bing query is good enough.

## 16. OpenClaw

OpenClaw remains an optional modular browser/extraction adapter, disabled by default. It must never block the main Scrapy pipeline and is not required for normal HTTP extraction.

## 17. Live job status

The UI reports job-scoped progress stages:
Discovery, URLs, Collection, Extraction, Validation, Qualification/Deduplication, Leads, Export.

The UI shows current stage, state, counts, recent activity, and terminal complete/failed state. Status reporting is observational and does not alter pipeline decisions.

## 18. Commercial multi-user isolation

Each job isolates search criteria, generated parameters, selected SERP sources, browser session state, harvested URL occurrences, crawl state, evidence, leads, exports, and progress events.

No global URL deduplication state may suppress another user's crawl input.

## 19. Persistence, authentication, and user data

V1.3 is a commercial multi-user application and must use persistent storage. PostgreSQL is the system-of-record database. Do not use in-memory Python dictionaries as the authoritative store for users, sessions, scraps, jobs, SERP captures, evidence, leads, or exports.

The backend owns authentication, authorization, user/session management, Current Scrap state, scraping jobs, SERP captures, URL occurrences, crawl pages, evidence, leads, and export history. The UI is a presentation layer over the FastAPI backend.

Core persistence entities include:
- users
- sessions
- wallets
- wallet_transactions
- application_settings / admin_settings
- scraps
- search_parameters
- serp_sources
- serp_results
- url_occurrences
- crawl_pages
- evidence
- leads
- lead_sources
- jobs
- exports

Commercial settings include an administrator-controlled Scrap creation price (default **$2.00**), administrator-controlled Premium SERP Extraction price (default **$1.00 per extraction**), and administrator-controlled maximum SERP result occurrences per Scrap (default **1,000**). These settings are persistent, auditable, and applied server-side. Client wallets and wallet transactions are persistent and isolated per client. Scrap creation charges must be atomic/idempotent so a retry cannot double-charge or create an uncharged Scrap.

The browser extension authenticates once and associates captures with the authenticated user’s active Current Scrap. Captures sync automatically; users must not copy capability tokens or press a Sync button during normal operation.

The UI must provide a dedicated Current Scrap workspace and persistent Scrap History. A Scrap is a persistent research workspace, not a search-engine execution record. Creating a Scrap and generating Google/Bing parameters does not execute a search, crawl a URL, or create a running Job. The Current Scrap page presents Manual SERP Discovery on the left and Premium SERP Extraction on the right as the two supported SERP acquisition paths.

### Commercial Scrap creation and wallet charging

Scrap creation is a billable user action. Each newly created Scrap costs a configurable amount from the authenticated client's wallet; the V1.3 default is **$2.00 per Scrap**. The price is an administrator-controlled setting and must not be hard-coded in the UI or pipeline.

Before creation, the backend must atomically verify sufficient wallet balance and reserve/debit the configured Scrap creation price. If funds are insufficient, creation is rejected and no Scrap is created. Wallet balance, pricing, charges, refunds/adjustments, and transaction history are persistent and strictly isolated per client. The UI must display the current wallet balance and the charge before confirming Scrap creation.

A client may own any number of Scraps, subject only to available wallet balance and the configured per-Scrap SERP limit. There is no fixed lifetime or total Scrap-count limit in V1.3.

### Scrap lifecycle and Current Scrap lock

A Scrap remains the user's Current Scrap until the user explicitly completes SERP URL submission. UI/session timeout, logout, browser restart, or re-login must not silently end or clear the Current Scrap. Current Scrap identity and lifecycle state are persisted in the backend, not held only in Streamlit session state.

The collection lifecycle is explicit:
```text
Collecting → Submitted → Running → Completed
                 ↓           ↘ Failed
                 ↓           ↘ Cancelled
                 └────────────→ terminal history
```

- **Collecting:** user may continue adding SERP sources/results. Research may be started against currently captured URL occurrences while collection continues.
- **Submitted:** user explicitly clicks **URL SUBMISSION COMPLETED**. No further SERP results may be attached to that Scrap. This action releases the Current Scrap lock and allows the user to create/select another Scrap.
- **Running:** Scrapy research is processing the URL occurrences already submitted/available to the job. A research job may run while the Scrap is still in Collecting state; completing URL submission closes discovery collection, not the already-started crawl.
- **Completed/Failed/Cancelled:** terminal research states retained in Scrap History.

An Active/Collecting Scrap with no Job is a created workspace awaiting human SERP discovery; it is not a running search. The UI must never clear this state merely because the user session expires. Scrap History must allow the user to reopen/select persistent Scraps, while Current Scrap always reflects the authenticated user's persisted active collection workspace.

A Scrap may contain multiple research jobs over its lifetime. Each job processes a bounded set of captured URL occurrences, preserving provenance. Starting a later job must not mutate or delete earlier job inputs/results, and duplicate destination URLs must not be re-submitted to the crawl engine.

### Commercial Premium SERP Extraction

Premium SERP Extraction is a billable action. The default price is **$1.00 per extraction request**. The price is administrator-controlled and must not be hard-coded in the UI or pipeline.

The user submits a Google or Bing search URL from the Premium SERP Extraction panel on the Current Scrap page. The backend validates the URL, identifies the provider, charges the configured premium extraction price atomically/idempotently, and sends the request to the configured SERP provider adapter.

The provider returns normalized SERP result occurrences, including destination URL and available result metadata/evidence. The backend validates the response, preserves result provenance, applies the per-Scrap SERP capacity, and loads accepted occurrences into the authenticated user's Current Scrap. Premium results then follow the exact same URL validation, crawling, evidence, extraction, qualification, deduplication, and export pipeline as manually harvested results.

Each premium extraction request is charged once. Retries of the same request must not double-charge. Provider failures must not create partial SERP imports or an uncharged/duplicated transaction.

Premium extraction is not an unlimited-results promise. The configured per-Scrap SERP limit remains authoritative, and provider pagination/depth is bounded by the configured limits. Duplicate destination URLs may remain visible as separate SERP occurrence/provenance records, but repeated normalized destination URLs are not submitted repeatedly to the crawl engine within the same Scrap.

The system must never implement CAPTCHA solving, CAPTCHA bypassing, search-engine credential/session theft, or other mechanisms intended to defeat Google/Bing anti-bot controls. Anti-bot handling is delegated to the contracted SERP provider.

### Per-Scrap SERP capacity

Each Scrap has a configurable maximum number of SERP result occurrences. The V1.3 default is **1,000 SERP results per Scrap**. The maximum is administrator-controlled and applies to the total persisted SERP result occurrences attached to that Scrap, across all imported pages/sources and collection sessions.

When the configured SERP capacity is reached, the backend must reject further SERP imports for that Scrap without deleting or deduplicating existing occurrences. The UI must show `SERP used / SERP limit` continuously and must prevent the extension/import workflow from silently exceeding the server-enforced limit.

The SERP capacity is independent from URL occurrence limits, crawl-page limits, and final Lead limits. Duplicate SERP destination URLs may be retained for occurrence/provenance accounting, but they do not create repeated crawl submissions within the same Scrap.

Completed, Failed, and Cancelled Scraps remain in history until retention or explicit deletion. Deleting a Scrap must not permit a previously charged creation fee to be reused unless an explicit administrator-controlled refund/credit policy exists.

Deleting a Scrap must delete its associated persisted SERP results/sources, URL occurrences, crawl pages, evidence, leads, lead sources, jobs, and exports through the persistence layer's ownership/cascade rules. Deletion must be scoped to the authenticated user and must never affect another user's data.

Scrap History is retained for more than one month but anything older than one month must be automatically purged. Retention is based on the scrap/result creation or completion timestamp defined by the persistence model. Purging must remove the associated historical data according to retention policy and must not affect active/current scraps.

Primary navigation should include:
- Dashboard
- New Scrap
- Current Scrap
- Scrap History
- Results
- Exports
- Settings

Advanced crawler/search controls remain configurable but should be placed behind an Advanced/Settings area so a new user can complete the normal lead-research workflow without understanding the underlying crawler architecture.

The client can add a prefix, remove a prefix, and view the currently blocked prefixes. ## 21. SERP capture behavior

The browser extension should continuously capture rendered Google/Bing result cards as they appear while the user browses. It should progressively scroll where the SERP permits, wait for new result cards, capture URL/title/snippet evidence, update the live captured count, and stop when the page reaches exhaustion/no-progress limits.

The extension must not open a new Scrappee tab for every capture. It should maintain one authenticated Scrappee context and automatically persist newly captured results to the user’s Current Scrap.

SERP snippets are first-class evidence. A snippet may contain useful lead attributes such as name, address, email, phone, role, company, or other contact information. Snippet evidence is retained with its SERP result provenance and may be used by deterministic extraction, enrichment, qualification, and validation alongside crawled page evidence.

1. Natural language produces SearchCriteria.

22. Wallet balances, charges, Scrap ownership, SERP limits, and lifecycle state are persistent and isolated between clients.
23. Scrap creation cannot double-charge on request retry and cannot create a Scrap without its required charge.
24. Current Scrap presents Manual SERP Discovery and Premium SERP Extraction side-by-side on the same page.
25. Pasting a Google/Bing search URL is exclusively a Premium SERP Extraction action; it is not part of free/manual discovery.
26. Premium SERP Extraction costs $1.00 per extraction by default and the price is administrator-configurable.
27. Premium extraction results load directly into the authenticated user's Current Scrap and use the same downstream pipeline as manually harvested SERP occurrences.
28. Premium extraction uses a provider adapter and never operates our own search-engine browser or CAPTCHA bypass.
29. Premium extraction is bounded by the per-Scrap SERP limit and configured pagination/depth controls, with exact duplicate destination URLs deduplicated before crawl submission.

## V1.3 Provider Configuration Addendum

Premium SERP Extraction has exactly four supported paid provider adapters:
- Serper
- DataForSEO
- SerpApi
- Bright Data

One provider is always designated the **default Premium SERP provider**. The default is administrator-configurable and is stored persistently; it is not selected by code or environment-variable hard-coding.

The initial seeded default is **Serper**, but this is only the initial configuration. Administrators may switch the default to DataForSEO, SerpApi, or Bright Data at any time.

Serper is the default Google SERP provider. Its API is provider-side Google search infrastructure; Scrappee does not operate or automate Google's search page. Serper credentials are entered by the administrator through the authenticated admin UI.

Provider credentials are **administrator-entered through the authenticated admin UI**. Provider credentials must never be hard-coded in source code, committed to the repository, or required in the deployment environment as provider secrets.

Provider credentials are persisted encrypted at rest. The application uses a server-side encryption key only for protecting stored provider credentials; that key is infrastructure secret material and is never exposed to customers or the UI.

The admin provider manager must show all four providers, configuration status, enabled/disabled state, and which provider is default. Secret values are never returned to the browser after saving; the UI may only show masked/configured status.

Premium extraction always resolves the current default provider from persistent configuration at request time and then invokes that provider's adapter. Provider failure handling remains bounded and must not silently switch providers unless an explicit future failover policy is added.

Provider-specific configuration may include credentials plus non-secret operational settings such as API endpoint, location, language, zone, or other provider-supported controls. These settings are administrator-controlled and persisted with the provider configuration.

All four adapters normalize provider-specific responses into the common `PremiumSerpItem` model before the result reaches the Premium extraction pipeline.


## V1.3 Live Scrapy Collection Observability

The Live Job Status contract is extended with genuine Scrapy worker telemetry. During the `Collection` stage, Scrappee must show incremental evidence that the Scrapy crawler is actually operating rather than displaying a static `Running` state while waiting for a blocking subprocess.

The Scrapy worker must emit bounded progress events as requests are processed. The application consumes those events while the worker is still running and reports, at minimum, worker state, submitted URL count, collected page count, failure count, latest crawler activity, and worker completion/failure. The UI must distinguish Collection not started, Scrapy running, Scrapy running with failures/no progress, Scrapy completed, and Scrapy failed.

A job must never claim that Scrapy is running after its worker has exited. Worker failures must produce a bounded diagnostic. Live collection telemetry is observational and must never modify crawl limits, URL occurrence handling, extraction, qualification, deduplication, or export decisions.

This section is part of the authoritative V1.3 specification and is implemented by the approved Live Job Status addendum.


### Collection Failure Semantics
A research job MUST NOT be marked `Completed` when Scrapy collection fails. Collection exceptions must propagate to the job controller, the job must enter `Failed`, and the persisted terminal diagnostic must retain the last bounded pipeline events and collection counters (`urls_submitted`, `pages_collected`, `pages_failed`). A zero-page result caused by a collector failure is not a successful research result.

### Reporting and crawl-failure transparency
- Results/History reporting must distinguish `URLs attempted`, `pages collected`, and `pages failed`.
- Every Scrapy URL occurrence must retain its collection outcome, HTTP status when available, content type, and exact failure reason when collection fails.
- Failure reasons must be grouped/countable and individual failed URLs must be inspectable from the reporting UI.
- Partial URL failures do not make the whole Scrapy job fail; the job is failed only when the Scrapy worker itself cannot complete/return a valid result.
- A Scrapy failure must never be silently converted into a successful zero-page job.
- `robots.txt` denial is a legitimate crawl outcome and must be reported explicitly; the system must not bypass robots restrictions.
