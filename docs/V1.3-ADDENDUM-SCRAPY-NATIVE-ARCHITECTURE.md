# Claw Scrapper — V1.3 Addendum: Scrapy-Native Architecture

**Status:** Approved architectural addendum to V1.3.
**Authority:** This document extends `V1.3-SOURCE-OF-TRUTH.md` and the bounded Scrapy crawl addendum.
**Purpose:** Make Scrapy the actual crawling framework, not merely an HTTP downloader invoked by custom Python code.

## 1. Architectural decision

Scrapy is the primary autonomous crawl engine after SERP URL collection.

Claw Scrapper must use Scrapy's mature crawling primitives wherever they fit the V1.3 requirements:
- scheduler and request queue
- downloader and downloader middleware
- spider and spider middleware
- request/response lifecycle
- retry and failure handling
- redirects and robots handling
- AutoThrottle and concurrency controls
- depth and bounded link traversal
- item pipelines
- extensions and signals
- StatsCollector
- conditional Playwright download handling
- crawl lifecycle and diagnostics

Custom Claw code remains responsible for business-domain behavior that Scrapy does not own.

## 2. System boundary

```text
Scrappee / Discovery
        ↓
valid SERP URL occurrences
        ↓
Claw Scrapper Crawl Controller
        ↓
Scrapy Spider
        ↓
Scrapy Scheduler
        ↓
Downloader Middleware
        ↓
HTTP Downloader
        ↓
conditional Playwright escalation when required
        ↓
Spider parse / bounded link expansion
        ↓
Scrapy Item Pipeline
        ↓
CrawlPage / evidence persistence
        ↓
Claw extraction + Pydantic + qualification
        ↓
lead deduplication + exports
```

Scrapy owns the crawl lifecycle between valid seed URL occurrences and collected crawl items.

Claw Scrapper owns search, billing, Scrap lifecycle, authentication, Lead semantics, extraction policy, validation, qualification, deduplication, persistence policy, and exports.

## 3. Responsibilities that remain outside Scrapy

The following remain Claw Scrapper responsibilities:
- Natural-language interpretation and SearchCriteria.
- Query Strategy Engine.
- Manual browser SERP Discovery.
- Premium SERP provider adapters.
- Scrap ownership and billing.
- URL validity policy before crawl submission.
- Client domain rules and generic mailbox policy.
- Lead Pydantic models and validation.
- Deterministic extraction and LLM research/correction.
- Lead qualification.
- Lead deduplication.
- PostgreSQL business records and ownership boundaries.
- CSV, Excel, and Google Sheets exports.
- Scrappee UI and authenticated user workflow.

These responsibilities must not be moved into Scrapy merely for architectural purity.

## 4. Scrapy scheduler is the crawl queue

Scrapy's scheduler is the authoritative crawl request queue during collection.

Do not create a second application-level crawl queue that duplicates scheduler decisions.

The Crawl Controller supplies bounded seed occurrences to the Spider. The Spider yields Requests. Scrapy schedules, orders, retries, and dispatches them.

Seed occurrences must not be discarded because another URL appears more useful. V1.3 has no lead-quality priority scorer.

## 5. Seed occurrence semantics

Every valid Discovery seed URL occurrence enters Scrapy subject to the configured maximum crawl URL-occurrence budget.

`max_crawl_pages` and `max_crawl_url_occurrences` are independent controls.

The implementation must not use `max_crawl_pages` to truncate the initial seed list. Page count limits collection/processing volume; URL-occurrence limits bound how many URL occurrences may enter the crawl.

Seed URL order/provenance must be retained.

## 6. URL deduplication rule

V1.3 requires exact destination-URL deduplication before crawl submission within a Scrap.

Repeated captures of the same normalized destination URL must not create repeated crawl
submissions. Distinct destination paths remain independent targets. SERP occurrence and
provenance records may remain available separately for auditability.

Scrapy's normal request fingerprinting may also deduplicate repeated URLs discovered during
internal-link expansion. No application-level rule may collapse distinct destination paths
or different users' crawl inputs.

## 7. Bounded internal-link expansion

The Spider is responsible for bounded same-domain navigation.

It may follow useful research paths including:
- contact
- team
- staff
- people
- management
- directory
- procurement
- purchasing
- sales
- buyer / buyers
- leadership
- about-us

Link selection is navigation control only.

It must never become a lead-quality score, semantic page-worthiness score, or discovery ranking system.

Seed URLs always retain their place in the crawl input. Internal links must not displace seeds.

## 8. Scrapy downloader middleware

Downloader middleware becomes the primary location for crawl-level request/response policies.

Use it for concerns such as:
- request headers/default browser-like headers where appropriate
- response classification
- retry policy extensions
- timeout/network diagnostics
- redirect diagnostics
- conditional browser escalation
- proxy integration if introduced later
- request/response telemetry

Do not reproduce Scrapy's built-in retry, redirect, cookie, compression, scheduler, or download behavior in custom application code unless a documented V1.3 requirement requires an extension.
## 9. Normal HTTP first; Playwright only when required

The default crawl path must use Scrapy's normal HTTP downloader.

Playwright must not be the global downloader for every HTTP/HTTPS request.

Browser rendering is an escalation mechanism for pages that genuinely require JavaScript or browser execution. Escalation may be triggered by explicit request metadata, a bounded middleware policy, or a bounded ReAct decision.

A rendered request must remain subject to the same crawl URL/page budgets and telemetry.

The system must avoid repeatedly escalating the same URL without a bounded reason.

## 10. Spider responsibilities

The Spider should remain focused on crawl navigation and response-to-item conversion:
- receive seed occurrences
- issue Requests
- process Responses
- classify collectable content
- discover bounded relevant internal links
- emit CrawlPage items
- expose crawl metadata to Scrapy stats

The Spider must not perform Lead extraction, LLM qualification, billing, or final Lead deduplication.

## 11. Item Pipeline

Collected crawl output must use a Scrapy Item Pipeline boundary.

The pipeline is responsible for handing normalized crawl items to the Claw persistence adapter and/or bounded downstream collection sink.

A crawl item must retain at minimum:
- URL
- request occurrence identity/index
- HTTP status
- content type
- raw document bytes where applicable
- HTML/text where applicable
- collection source
- collection error
- crawl depth
- relevant request metadata

Persistence failures must be surfaced as collection/worker failures rather than silently producing a successful crawl.

## 12. Documents

Scrapy remains the document acquisition engine.

For PDF, DOCX, CSV, XLS, and XLSX, Scrapy acquires the response bytes and metadata. Mature format-specific parsers remain downstream:
- PDF → `pypdf`
- DOCX → `python-docx`
- CSV/XLS/XLSX → `pandas`

No second document crawler is introduced.

A document parse failure is an evidence/diagnostic outcome and must not terminate an otherwise healthy crawl.

Legacy `.DOC` remains unsupported in V1.3.

## 13. Scrapy StatsCollector

Scrapy StatsCollector is the authoritative source for crawl-level runtime telemetry.

At minimum, collection reporting should expose:
- URL occurrences submitted
- requests scheduled/enqueued
- requests downloaded
- successful responses
- failed responses
- HTTP status counts
- retries
- robots denials
- timeouts
- network/DNS/TLS failures where classifiable
- redirects
- browser escalations
- items collected
- crawl depth information
- finish reason
- elapsed crawl time

Raw Scrapy stats may remain internal; the UI receives a bounded, safe projection.

## 14. Scrapy signals and extensions

Scrapy signals/extensions are the preferred lifecycle telemetry mechanism.

Use signals such as spider-opened, response-received, request-dropped, and spider-closed to generate bounded job events.

Telemetry must observe the crawl. It must not modify crawl decisions, limits, qualification, or Lead output.

The application may stream a bounded projection of Scrapy stats to the existing Live Job Status event sink.

## 15. Retry and failure model

Scrapy's retry middleware is the primary retry mechanism.

Retry policy must remain configurable and bounded.

Failure classes must distinguish, where observable:
- robots.txt denial
- HTTP 4xx
- HTTP 5xx
- timeout
- DNS failure
- connection failure
- TLS/SSL failure
- redirect failure
- browser/render failure
- document acquisition failure
- worker/process failure

An individual URL failure does not fail the entire crawl.

A Scrapy worker/process failure does fail the Collection stage and therefore the research job.

A robots denial is a legitimate policy outcome and must never be bypassed.
## 16. AutoThrottle and concurrency

Scrapy's AutoThrottle and concurrency controls are the default crawl-rate mechanisms.

Configured limits remain administrator-controlled through Claw Scrapper's operational settings where exposed by V1.3.

The implementation must prefer Scrapy's per-domain concurrency, download delay, retry, timeout, and AutoThrottle mechanisms over custom sleep loops or handcrafted request pacing.

Crawler limits are safety and cost controls, not lead-quality controls.

## 17. Depth and exhaustion controls

Scrapy depth handling may be used to bound internal-link expansion.

Depth is a navigation bound only. It must never rank or reject pages because of expected Lead quality.

Exhaustion/no-progress controls remain part of V1.3 and must be observable in final reporting.

The crawler must terminate deterministically when its configured page, URL-occurrence, depth, pagination, or exhaustion bounds are reached.

No infinite link-following loop is permitted.

## 18. Crawl reporting

The Collection report must be derived from Scrapy lifecycle data rather than a single final success/failure flag.

The report must make the following distinction explicit:

```text
URL occurrences submitted
        ↓
requests scheduled
        ↓
responses downloaded
        ↓
successful pages/items
        ↓
failed pages/items
        ↓
downstream extraction
```

For failures, the UI must show grouped reason counts and allow inspection of individual failed URL occurrences.

The terminal report must state the Scrapy finish reason and retain a bounded diagnostic when the worker fails.

## 19. Process boundary

A separate Scrapy worker process is acceptable for isolation, but the process boundary must not strip Scrapy of its native capabilities.

The current stdout marker protocol (`CLAW_PROGRESS` / `CLAW_RESULT`) is an implementation detail, not the architectural telemetry model.

If retained temporarily, it must carry a bounded projection of Scrapy StatsCollector/signals and not replace them.

The long-term design should make the Scrapy worker produce structured crawl output and telemetry through explicit interfaces rather than custom ad-hoc queue logic.

## 20. PostgreSQL boundary

PostgreSQL remains the Claw Scrapper system of record.

Scrapy does not become the owner of users, Scraps, wallets, jobs, Leads, client policies, or exports.

Scrapy's scheduler/state may be used for crawl execution, but business persistence must remain under Claw's PostgreSQL model.

Any Scrapy-native persistence feature must not create a second authoritative database for business state.

## 21. ReAct boundary

The ReAct loop remains above the crawler as an autonomous control layer:

```text
Observe → Evaluate → Choose → Execute → Observe
```

ReAct may decide bounded actions such as whether a page requires browser escalation or whether a bounded research/enrichment step is needed.

It must not override hard crawl limits, robots policy, URL-occurrence semantics, Pydantic validation, or user/client isolation.

Scrapy performs deterministic crawl mechanics; ReAct provides bounded adaptive decisions around them.

## 22. OpenClaw boundary

OpenClaw remains optional and modular.

It may be used for browser-specific interaction/extraction when normal HTTP plus conditional Playwright is insufficient.

OpenClaw must not replace Scrapy's scheduler, downloader, retry system, link traversal, crawl bounds, or crawl telemetry.

Normal V1.3 crawling must work without OpenClaw.

## 23. Code that should be removed or reduced

During implementation, identify and remove/reduce custom code that duplicates mature Scrapy behavior, including:
- custom crawl queues
- custom retry loops
- custom request pacing/sleep loops
- duplicate redirect handling
- duplicate response scheduling
- global Playwright handling for ordinary HTTP pages
- ad-hoc crawl counters where Scrapy stats provide the value
- custom link traversal queues that bypass Scrapy Requests
- custom worker progress logic that ignores Scrapy signals/stats

Do not remove Claw-specific business policy merely because it can technically be expressed as Scrapy middleware.
## 24. Implementation phases

### Phase 1 — Crawl engine correction

1. Make all valid seeds enter Scrapy up to the URL-occurrence budget.
2. Deduplicate repeated normalized destination URLs before crawl submission while preserving occurrence/provenance records.
3. Move ordinary HTTP requests back to Scrapy's standard downloader.
4. Make Playwright conditional rather than global.
5. Make retry, timeout, redirect, robots, and throttling policies Scrapy-native.
6. Establish complete StatsCollector metrics.

### Phase 2 — Native crawl lifecycle

1. Use Scrapy signals/extensions for collection lifecycle telemetry.
2. Use Item Pipeline as the crawl-item boundary.
3. Persist every attempted URL occurrence outcome, including failures.
4. Implement bounded same-domain link expansion through Spider Requests.
5. Expose crawl statistics and failure reasons through the existing reporting API/UI.

### Phase 3 — Hardening

1. Evaluate Scrapy persistent crawl state/JOBDIR for pause/resume where compatible with Scrap lifecycle.
2. Remove remaining duplicate custom crawler machinery.
3. Add failure-injection tests for robots, HTTP, timeout, DNS/network, retry exhaustion, and worker failure.
4. Add performance tests for large URL-occurrence sets and repeated URL occurrences.
5. Verify multi-user isolation and PostgreSQL persistence under concurrent jobs.

No phase may change V1.3 Lead qualification, URL deduplication, billing, or export rules.

## 25. Required tests

The implementation is not complete until tests verify:
- all valid seeds are submitted subject to URL budget;
- page limit does not silently truncate the seed list;
- repeated seed URLs are represented in occurrence/provenance data but are not submitted repeatedly to the crawl engine;
- repeated internal-link occurrences are not silently deduplicated;
- internal links remain same-domain and bounded;
- depth limits terminate traversal;
- normal HTTP does not launch Playwright unnecessarily;
- explicit browser escalation works;
- retries remain bounded;
- robots denial is recorded without bypass;
- HTTP/network/timeout failures are classified and persisted;
- Scrapy worker failure makes the research job fail;
- partial URL failures do not fail a healthy worker;
- Scrapy stats reach live reporting;
- crawl items reach the persistence boundary;
- document bytes remain available to downstream parsers;
- no Lead is created directly by the crawler;
- multi-user crawl data remains isolated.

## 26. Acceptance criteria

V1.3 Scrapy-native architecture is accepted when:

1. Scrapy is the authoritative crawl scheduler/request engine after URL discovery.
2. All unique valid destination URLs enter Scrapy subject to the configured crawl URL budget; duplicate occurrences remain available for provenance.
3. `max_crawl_pages` and `max_crawl_url_occurrences` remain independent.
4. Exact duplicate destination URLs are removed from repeated crawl submission within a Scrap; distinct paths remain independent.
5. Same-domain internal-link expansion is performed by Scrapy Requests and remains bounded.
6. Normal pages use Scrapy's HTTP downloader.
7. Playwright is an explicit bounded escalation, not the default downloader.
8. Scrapy middleware owns crawl-level retry/response/request policies where applicable.
9. Scrapy StatsCollector and signals provide crawl telemetry.
10. Scrapy Item Pipeline is the crawl-item boundary.
11. Crawl failures are classified, persisted, and visible in reporting.
12. Worker failure cannot become a successful zero-page research job.
13. PostgreSQL remains the business system of record.
14. Extraction, Pydantic validation, qualification, Lead deduplication, and exports remain downstream of collection.
15. OpenClaw remains optional and cannot block normal crawling.
16. No custom component duplicates mature Scrapy behavior without a documented V1.3 reason.

## 27. Architectural rule

**Use Scrapy first. Customize only where Claw Scrapper has a requirement Scrapy does not provide.**

This addendum is controlling for the crawler implementation and must be read together with `V1.3-SOURCE-OF-TRUTH.md`, `V1.3-ADDENDUM-BOUNDED-SCRAPY-CRAWL.md`, and the approved Live Job Status addendum.
