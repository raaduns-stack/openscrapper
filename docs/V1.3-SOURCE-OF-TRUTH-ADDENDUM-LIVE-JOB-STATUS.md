# V1.3 Addendum — Live Job Logging/Status

**Status:** Approved implementation addendum to V1.3.

## Purpose

Scrappee must expose live pipeline progress in the customer-facing UI.
The UI must show the active job progressing through Discovery, URLs,
Collection, Extraction, Validation, Qualification/Dedupe, Leads, and Export.

## Requirements

- Pipeline stages emit structured progress events through an application-level event sink.
- Events are job-scoped and bounded; they must not create an unbounded log stream.
- The UI renders current stage, status, counts, and recent activity while the job runs.
- The status view must not alter discovery, collection, extraction, validation,
  qualification, deduplication, or export decisions.
- Existing V1.3 operational limits remain the governing safety controls.
- Existing CLI/API behavior remains valid; this adds observability for Scrappee.

## Minimum event stages

1. Discovery
2. URLs
3. Collection
4. Extraction
5. Validation
6. Qualification/Deduplication
7. Leads
8. Export

## Failure and completion

Jobs expose terminal `completed` or `failed` state with the final lead count
and a bounded diagnostic message when failed.


## Live Scrapy Collection Observability

Scrapy collection must expose genuine live progress while the crawler is running; a job must not remain at `URLs` with `Pages = 0` merely because the application is waiting for a blocking crawler subprocess to finish.

During Collection the backend must report, at minimum:
- Scrapy worker started/running state;
- URL occurrences submitted to Scrapy;
- pages successfully collected;
- page/request failures;
- bounded last-activity information identifying the latest collected URL or crawler event;
- Scrapy worker completion or failure.

Progress events must be emitted incrementally from the Scrapy worker while requests are processed, not synthesized only after the subprocess exits. The parent application must consume these events without waiting for the complete crawl result.

The customer-facing UI must therefore make it possible to distinguish:
1. Collection has not started;
2. Scrapy is actively running;
3. Scrapy is running but requests are failing/no-progress;
4. Scrapy has completed;
5. Scrapy has failed.

The persisted job event stream remains bounded. Live Scrapy telemetry is observational only and must not change crawl limits, URL occurrence handling, extraction, qualification, deduplication, or export decisions.

A valid live Collection state must never claim Scrapy is running when the Scrapy worker has exited. Terminal collection diagnostics must preserve the worker failure reason in bounded form.
