# ADR-0001: V1.2 Collection and Browser Architecture

- **Status:** Accepted
- **Date:** 2026-09-07
- **Scope:** V1.2 MVP

## Context

The earlier prototype centered collection around browser automation. V1.2 requires a
clear separation between SERP discovery/capture, high-volume collection/enrichment,
rendering, extraction, research, and browser interaction. In the current product workflow,
Google/Bing SERP discovery is performed in the browser and captured by the extension;
Scrapy begins after URL capture.

## Decision

Adopt the following production flow for the current product workflow:

```text
Google/Bing SERP -> browser extension capture -> candidate qualification
    -> persistent leads -> all captured SERP URLs -> controlled Scrapy enrichment
    -> Evidence -> deterministic extraction -> LLM if needed
    -> OpenClaw if browser interaction is needed -> qualification
    -> Pydantic/self-correction -> dedupe/merge -> export
```

The browser extension's captured SERP URLs are the primary research discovery input.
Start Research submits all captured SERP URLs to the enrichment engine.

Scrapy is responsible for efficiently fetching supplied URLs and performing controlled
internal enrichment. It may discover additional qualifying people, but crawling must be
bounded by explicit depth, page/URL, time, domain, and relevant-link limits. Unbounded
recursive crawling is prohibited.

Lead qualification is evidence-based and source-agnostic. The exact contract is:

```text
(first_name OR last_name)
AND
at least ONE of:
position, company_name, phone, city, state, country, website
```

A personal email is optional; if present, it must be personal. SERP and Scrapy use the
same qualification contract. Email-only, company-only, and name-only records are rejected.

All lead creation and updates use one authoritative dedupe/persistence path.

The Leads UI exposes a per-lead Enrich action that invokes the same enrichment engine used
by batch research.

OpenClaw remains encapsulated behind a browser adapter and is invoked only when HTTP
and rendering are insufficient and browser interaction is required.

## Consequences

Positive:
- High-volume collection is separated from browser automation.
- Browser cost is limited to cases that need interaction.
- Search providers can be replaced without redesigning collection.
- Evidence and deterministic extraction remain independently testable.

Required follow-up:
- Complete Scrapy collection.
- Complete scrapy-playwright integration.
- Strengthen ReAct, self-correction, evidence, and production orchestration.
- Add Google Sheets and customer-facing search workflow.
