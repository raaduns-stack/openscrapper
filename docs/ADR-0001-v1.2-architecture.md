# ADR-0001: V1.2 Collection and Browser Architecture

- **Status:** Accepted
- **Date:** 2026-09-07
- **Scope:** V1.2 MVP

## Context

The earlier prototype centered collection around browser automation. V1.2 requires a
clear separation between discovery, high-volume collection, rendering, extraction,
research, and browser interaction.

## Decision

Adopt the following production flow:

```text
Search -> URLs -> Relevance -> Scrapy/HTTP -> Playwright if needed
-> Evidence -> Deterministic extraction -> LLM if needed
-> OpenClaw if browser interaction is needed -> Qualification
-> Pydantic/self-correction -> Dedupe -> Export
```

Discovery is responsible for searching the internet and producing candidate URLs.
Scrapy is responsible for efficiently fetching/crawling those URLs.

OpenClaw remains encapsulated behind a browser adapter and is invoked only when HTTP
and rendering are insufficient and browser interaction is required.

## Consequences

Positive:
- High-volume collection is separated from browser automation.
- Browser cost is limited to cases that need interaction.
- Search providers can be replaced without redesigning collection.
- Evidence and deterministic extraction remain independently testable.

Required follow-up:
- Complete Scrapy collection.
- Complete scrapy-playwright integration.
- Strengthen ReAct, self-correction, evidence, and production orchestration.
- Add Google Sheets and customer-facing search workflow.
