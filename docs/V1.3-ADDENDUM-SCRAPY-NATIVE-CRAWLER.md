# Claw Scrapper V1.3 — Scrapy-Native Crawler Addendum

**Status:** Authoritative V1.3 implementation addendum.
**Purpose:** Make Scrapy the actual crawling framework rather than a thin downloader wrapper.

## 1. Decision
Scrapy is the primary crawl engine after SERP URL collection. Claw Scrapper must use Scrapy-native capabilities wherever they belong. Custom code must not reimplement scheduler, retry, throttling, response handling, link scheduling, crawl statistics, or crawl lifecycle behavior already provided by Scrapy.

## 2. Ownership boundary
### Claw Scrapper owns
- SearchCriteria/query strategy, SERP acquisition, Scrap lifecycle, billing, permissions and limits.
- URL validity policy and URL-occurrence accounting.
- PostgreSQL system of record.
- Evidence-to-lead extraction, LLM research, Pydantic validation, qualification, lead deduplication and exports.

### Scrapy owns
- Request scheduling and concurrency.
- Downloader, redirects, retries, timeouts and HTTP response handling.
- Robots policy and per-domain throttling/AutoThrottle.
- Same-domain navigation and bounded link discovery.
- Crawl depth/navigation bounds.
- Request/response failure classification.
- Crawl statistics and lifecycle signals.
- Document acquisition as raw bytes.
- Conditional Playwright escalation through Scrapy request/download-handler integration.

## 3. Required crawl flow
```text
Valid SERP URL occurrences → Scrapy Spider seeds → Scrapy Scheduler → Downloader Middleware → HTTP downloader → conditional Playwright → Spider response handling → bounded same-domain links → CrawlPageItem → Item Pipeline → PostgreSQL crawl/evidence persistence → existing extraction/validation/qualification
```

## 4. Seed semantics
Every valid Discovery URL occurrence enters the Scrapy scheduler subject only to the configured **max crawl URL occurrences** limit. `max crawl pages` is a separate response-processing limit. It must not truncate the initial seed list before scheduling. Seed occurrences are never displaced by internal-link expansion.

## 5. URL occurrence semantics
**SERP occurrence preservation does not mean repeated crawling.** Before Scrapy, V1.3 performs exact destination-URL deduplication within each Scrap: repeated captures of the same normalized destination URL do not create repeated crawl submissions. Distinct destination paths remain independent targets. Provenance/occurrence metadata remains available separately from crawl submission identity.

Once those seed occurrences enter Scrapy, normal Scrapy duplicate-request filtering **is allowed** for URLs discovered through recursive/internal-link expansion. Repeated internal links to a URL that has already been scheduled do not need to be crawled repeatedly. This crawler-level URL deduplication is an efficiency mechanism only; it must not delete, merge, or rewrite the original SERP occurrence records or their provenance.

Lead deduplication remains downstream after extraction and qualification.

## 6. Link expansion
The Spider may follow relevant same-domain links such as contact, team, staff, people, management, directory, procurement, purchasing, sales, buyer, leadership and about-us. This is navigation control only. There is no lead-quality page scorer or semantic page-worthiness threshold. Expansion is bounded by configured URL/page/depth/exhaustion limits.

## 7. HTTP first, browser second
Normal HTTP is the default Scrapy acquisition path. Playwright must not be globally installed as the downloader for every HTTP request. Browser rendering is an explicit escalation for pages requiring JavaScript/browser behavior or an explicit rendered request.

## 8. Middleware
Use Scrapy downloader/spider middleware for retry policy, request/response classification, headers, rendering escalation and crawl instrumentation. Do not duplicate these concerns in the application controller.

## 9. Item pipeline
Responses are normalized into a crawl item containing URL occurrence identity, URL, status, content type, raw body/content, source, error state and crawl metadata. Item pipelines handle collection persistence/normalization before the existing lead-extraction pipeline. PostgreSQL remains the authoritative application store.

## 10. Stats and signals
Scrapy StatsCollector and signals are the authoritative crawl telemetry source. Persist a bounded job-scoped projection containing at minimum: requested/scheduled, downloaded, successful, failed, retries, robots-denied, HTTP failures, timeouts/network failures, redirects, documents, browser escalations, depth/expansion counts and terminal state. UI consumes this projection and never changes crawl decisions.

## 11. Failure semantics
- Individual URL failure: crawl continues and is reported as a per-URL failure.
- Robots denial: expected policy outcome; report explicitly, not as a worker crash.
- HTTP 4xx/5xx: retain response/failure metadata and continue within policy.
- Timeout/DNS/TLS/network failure: retain reason and continue within policy.
- Scrapy worker/process failure: job fails with terminal diagnostic.
- Partial crawl with successful pages and failed URLs: job completes with partial-failure reporting.

## 12. Playwright
Use `scrapy-playwright` conditionally. Static HTTP acquisition remains the normal path. Browser escalation must be bounded and observable. OpenClaw remains an optional modular browser adapter and must never be required for the normal Scrapy crawl.

## 13. Persistence and process isolation
A subprocess boundary is acceptable for worker isolation during V1.3, but the boundary must transport Scrapy-native stats/items/events rather than forcing the application to recreate Scrapy's scheduler and crawl telemetry. Future pause/resume may use Scrapy JOBDIR where compatible with PostgreSQL job state.

## 14. Remove/replace from current implementation
- Manual application-level crawl queue/round loop as the primary scheduler.
- Global Playwright download handler for all HTTP requests.
- Ad-hoc retry behavior outside Scrapy.
- Custom stdout progress as the primary telemetry model; retain only as worker transport if needed.
- Application-level URL duplicate suppression.
- Seed truncation by `max_pages`.
- Lead-quality priority scoring in the crawl scheduler.

## 15. Acceptance criteria
1. All unique valid destination URLs are submitted to Scrapy up to the configured crawl URL limit; duplicate occurrences remain available for provenance.
2. `max crawl pages` and `max crawl URL occurrences` remain independent.
3. No original SERP URL occurrence is silently removed before or at seed submission; Scrapy may deduplicate repeated URLs discovered during recursive/internal-link expansion.
4. Scrapy scheduler/concurrency/retry/redirect/robots/throttle behavior is active.
5. Relevant same-domain links are scheduled by the Spider, not an application crawl loop.
6. Normal HTTP requests do not launch Playwright.
7. Browser escalation is conditional and measurable.
8. Crawl stats/signals produce live reporting counters and terminal diagnostics.
9. Per-URL failures are retained with reasons.
10. Worker failures are distinct from per-URL failures.
11. Documents are acquired by Scrapy as raw bytes and parsed downstream by mature format-specific libraries.
12. Existing extraction, Pydantic validation, qualification, lead deduplication and export behavior remains intact.
13. Existing V1.3 billing, Scrap lifecycle, URL deduplication removal and multi-user rules remain unchanged.

## 16. Implementation order
**Phase A:** seed/occurrence semantics, HTTP-first downloader, middleware, retries and Scrapy-native stats/signals.

**Phase B:** Spider-driven link expansion, item model/pipeline and PostgreSQL collection persistence.

**Phase C:** conditional Playwright escalation, richer crawl reporting and bounded browser diagnostics.

**Phase D:** optional Scrapy JOBDIR pause/resume after PostgreSQL job lifecycle is proven stable.
