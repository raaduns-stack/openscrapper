## 4. Approved V1.3.1 Delta — Incremental Evidence and Lead Processing During Crawl

**Status:** CTO-approved engineering delta, 2026-09-18.

### Problem
The current implementation waits for the complete Scrapy collection result before beginning downstream evidence construction, extraction, validation, qualification, and lead persistence. This leaves evidence/leads at zero while Scrapy may still be processing pages and prevents downstream research processing from operating incrementally.

### Decision
Research processing MUST be incremental while Scrapy collection is active. Each successfully collected crawl item MUST enter evidence construction, extraction, validation, qualification, and lead persistence as it becomes available. The system MUST NOT require the complete Scrapy crawl to finish before processing collected pages.

### Authoritative runtime flow
```text
SERP URL occurrence (seed)
        ↓
Scrapy Scheduler / Downloader
        ↓
Crawl response / CrawlPageItem
        ↓
Persist crawl outcome
        ↓
Evidence construction
        ↓
Deterministic extraction → LLM when necessary
        ↓
Pydantic Lead validation
        ↓
Qualification
        ↓
Lead deduplication / upsert
        ↓
Persist evidence + lead
        ↓
Publish live counters/events
        ↓
Scrapy continues crawling/discovering
```

Collection and research operate as a concurrent streaming pipeline, not as two serial phases.

### Required behavior
1. Scrapy remains the authoritative crawl scheduler and request engine.
2. A collected page/document MUST be available to downstream processing without waiting for unrelated crawl requests to finish.
3. Evidence MUST be persisted incrementally as pages arrive.
4. Lead candidates MUST be extracted, validated, qualified, and persisted incrementally as evidence arrives.
5. Lead deduplication MUST operate incrementally while retaining the existing final deduplication guarantee.
6. The UI MUST expose live incremental `pages`, `evidence`, and `leads` counts while the crawl is still running.
7. A page producing no lead remains valid evidence and must not block or fail the crawl.
8. A failed page/request remains a recorded crawl outcome and must not prevent other pages from downstream processing.
9. Backpressure MUST be bounded so downstream extraction cannot create an unbounded in-memory queue.
10. Cancellation MUST stop crawl scheduling and downstream processing cleanly while preserving already persisted results.
11. Worker/process failure MUST preserve already persisted crawl outcomes, evidence, and leads; terminal state must distinguish partial progress from successful completion.
12. Scrapy StatsCollector remains authoritative for crawl telemetry; downstream pipeline counters are authoritative for evidence/lead telemetry.
13. No page-count or URL-count limit may be invented as a substitute for streaming. Existing documented crawl controls remain the governing bounds.
14. Every valid submitted SERP URL occurrence remains a crawl seed subject to configured crawler controls; a seed is not a page-only target.
15. The existing V1.3 responsibility boundary remains unchanged: Scrapy owns crawling; Claw owns evidence interpretation, extraction, Pydantic validation, qualification, lead deduplication, persistence, and exports.

### Non-goals
- No new arbitrary page cap.
- No new URL deduplication.
- No semantic lead-quality crawl priority scorer.
- No replacement of Scrapy's scheduler with an application-level queue.
- No requirement that every crawl page produce a lead.
- No change to Google/Bing CAPTCHA handling.
- No CRM synchronization.

### Acceptance criteria
1. During an active crawl, the UI can show `pages > 0` while Scrapy is still running.
2. During the same active crawl, `evidence` increases as collected pages are processed; it does not remain zero until crawl completion.
3. During the same active crawl, `leads` increases when qualifying candidates are found; it does not wait for crawl completion.
4. A crawl continuing to discover URLs does not block already collected pages from evidence/extraction processing.
5. A downstream extraction error for one page does not stop processing subsequent pages.
6. Persisted evidence and leads survive worker interruption/restart without duplicate persistence of the same occurrence/candidate.
7. Final completion performs reconciliation/final deduplication and export over the incrementally persisted result set.
8. Live job telemetry distinguishes crawl progress from downstream evidence/lead progress.
9. Tests prove incremental processing with a crawl that emits multiple pages before collection completes.
10. Tests prove bounded backpressure and clean cancellation/error handling.

### Migration impact
This is a pipeline execution-model change only. Existing Scrap, SERP occurrence, crawl-page, evidence, Lead, qualification, deduplication, and export schemas remain authoritative unless a later approved delta explicitly changes them. Existing batch collection interfaces may remain temporarily as compatibility boundaries, but production research execution MUST NOT depend on receiving the complete crawl list before downstream processing begins.

### Implementation gate
No coding begins from this delta until the implementation plan is reviewed against the V1.3 Source of Truth, approved Scrapy addenda, Scrapy implementation audit, and this delta. Existing code is not authoritative where it conflicts with this delta.

## 8. Approved V1.3.1 Delta — Senders Module

**Status:** CTO-approved architecture, 2026-09-25.

### Problem

Scrappee currently has lead research, enrichment, exports, billing, and Scrap workflows, but no dedicated outbound email sender subsystem. Email sending configuration, mailbox authorization, campaign execution, letters/templates, and reply routing must be introduced without coupling them to the crawler or duplicating existing Lead/Scrap persistence behavior.

### Decision

Introduce a new top-level **Senders** product module with its own bounded backend services and UI pages.

```text
Senders
├── Sending Summary
├── Sender Configuration
│   ├── SMTP
│   ├── Gmail OAuth
│   └── Microsoft / Hotmail OAuth
├── Campaign Details
├── Letters
└── Reply To
```

Senders consumes existing persisted Leads/Campaign selections but does not modify the authoritative Scrap research pipeline.

### 8.1 Architecture boundary

Senders remains separate from SERP discovery, Scrapy collection, evidence, extraction, qualification, deduplication, enrichment execution, and Scrap lifecycle.

Existing Lead records remain authoritative. Senders may reference Leads and campaigns but must not create an alternate Lead model.

Initial backend boundary:

```text
src/senders/
├── models
├── service
├── smtp
├── gmail
├── microsoft
└── reply
```

Exact module names may change if the responsibility boundary remains intact.

### 8.2 Sender accounts

A Sender represents one outbound sending identity owned by the authenticated user.

Supported types:

1. SMTP
2. Gmail OAuth
3. Microsoft OAuth, including supported Hotmail/Outlook consumer accounts

Persistent sender state includes ID, owner, display name, email, provider type, enabled state, connection/health status, and timestamps.

Ownership MUST be enforced server-side.

### 8.3 SMTP

SMTP configuration supports host, port, TLS/SSL mode, username, credential/app-password, sender email, display name, and connection test.

SMTP secrets MUST NOT be returned to the frontend after storage.

### 8.4 Gmail OAuth

Gmail MUST use OAuth rather than collecting a normal account password.

The implemented web flow uses server-controlled Google OAuth authorization-code exchange, a single-use expiring state bound to the authenticated user and sender, backend-only encrypted token storage, no frontend exposure of client secrets/tokens, authenticated-user ownership, reconnect/re-authorize, and disconnect/revocation handling.

The initial Gmail scope is `https://www.googleapis.com/auth/gmail.send`, limited to sending mail on behalf of the authorized account. Google documents this as a sensitive Gmail scope and requires OAuth consent/configuration appropriate to the deployment. The production redirect URI is `https://scrapee.uk/oauth/gmail/callback`.

OAuth scopes MUST be minimized to the approved sending/reply functionality.

### 8.5 Microsoft / Hotmail OAuth

Microsoft/Hotmail MUST use Microsoft OAuth with the same security boundary as Gmail: protected state validation, backend-only token storage, no secret exposure, ownership enforcement, reconnect/disconnect, and safe account-status reporting.

Supported account types and exact permissions MUST be verified during implementation before coding the provider integration.

### 8.6 Credential security

Provider credentials, OAuth tokens, SMTP passwords, and equivalent secrets MUST never be returned by normal APIs, exposed to browser-local configuration, or written to logs.

Secrets MUST use encrypted-at-rest storage where supported by the deployment. They MUST be scoped to the owning user and removed/revoked on disconnect according to provider capability.

### 8.7 Campaign Details

Campaigns reference existing Leads.

A campaign supports campaign ID, owner, name, selected sender(s), selected Leads or selection criteria, selected Letter, status, sending schedule/configuration, sending limits, and timestamps.

Sending MUST NOT alter Lead qualification/completion state.

Campaign execution MUST retain enough sending state to prevent accidental duplicate sends when an action is retried.

### 8.8 Letters

Letters are reusable outbound templates supporting name, subject, body, HTML/plain text as applicable, personalization variables, signature, owner, active/archive state, and timestamps.

Personalization is resolved from Lead/campaign context at send time.

Template/rendering failure MUST prevent that message from being sent and MUST be persisted as a bounded failure.

### 8.9 Reply To

Reply-To supports a sender-level default and an explicitly configured campaign-level override.

The effective Reply-To used for each outbound message MUST be persisted.

Reply handling MUST preserve association with the originating sender/campaign/message whenever provider metadata permits.

### 8.10 Sending Summary

Sending Summary is observational and MUST use persisted backend state.

Initial metrics: total senders, active/inactive senders, queued messages, sent messages, successful sends, failures, replies, provider-exposed bounce/delivery outcomes, campaign activity, and sender health.

Frontend-local counters are not authoritative.

### 8.11 Sending limits and scheduling

Sending limits MUST be explicit configuration.

Before production sending is enabled, CTO approval is required for per-sender daily/hourly limits, campaign limits, retry policy, scheduling/time-zone behavior, provider throttling, and bounce/failure handling.

No unapproved sending-limit values may be invented.

### 8.12 API boundary

Initial namespace:

```text
GET/POST /senders
GET/PATCH/DELETE /senders/{sender_id}
POST /senders/{sender_id}/test
POST /senders/{sender_id}/oauth/...
GET/POST /campaigns
GET/PATCH/DELETE /campaigns/{campaign_id}
GET/POST /letters
GET/PATCH/DELETE /letters/{letter_id}
GET/POST /replies/...
GET /sending-summary
```

Exact schemas MUST be derived during implementation and added to the API handoff.

### 8.13 Persistence boundary

Senders uses persistent PostgreSQL state.

The implementation will require separate persistence for sender accounts, provider credential/token metadata, campaigns, letters, campaign/Lead membership or recipient selection, outbound messages/send attempts, and reply/message linkage.

Exact table names/indexes are implementation details.

All user-owned records MUST be isolated by authenticated user ID.

### 8.14 Failure and retry

Outbound sending MUST be idempotent at the message-attempt boundary.

A retry MUST NOT silently create a second successful send for a message already accepted by the provider.

Provider failures, authentication failures, rate limits, invalid recipients, and template failures MUST be distinguishable.

Invalid/revoked credentials MUST place a sender into an unhealthy/reauthorization-required state rather than allowing indefinite retries.

### 8.15 Non-goals

This delta does not approve CRM synchronization, autonomous lead generation, changes to the Scrapy pipeline, replacement of the Lead model, automatic enrichment during sending, CAPTCHA handling, arbitrary bulk sending without campaign controls, unapproved sending limits, or provider-specific assumptions before capability verification.

### 8.16 Acceptance criteria

1. Dedicated Senders UI exists without affecting Scrap workflows.
2. Campaign creation can select existing completed Leads owned by the authenticated user, and selected Lead membership is persisted without creating duplicate Lead records.
3. SMTP sender can be configured without exposing its password after save.
4. Gmail OAuth can connect and display mailbox identity/status.
5. Microsoft/Hotmail OAuth can connect and display identity/status for supported account types.
6. Sender ownership is server-enforced.
7. Provider secrets/tokens are never returned through normal APIs.
8. Campaigns reference existing Leads without duplicate Lead records.
9. Letters render personalization without modifying the Lead.
10. Effective Reply-To is persisted with outbound-message state.
11. Summary metrics come from persisted state.
12. Failed sends are persisted with bounded diagnostics.
13. Retry behavior is idempotent.
14. Invalid/revoked authorization stops repeated attempts and exposes reauthorization state.
15. Existing Scrap research behavior remains unchanged.
16. API/database implementation details are documented and tested against this delta.

### 8.17 SMTP sending implementation boundary

The first outbound-send slice is deliberately limited to an explicit one-Lead SMTP test send from a draft campaign. It does not yet perform automated campaign bulk sending, scheduling, provider throttling, or retry automation. Each test send has a persisted idempotency key and `sending` state; an uncertain send is not silently retried.

### 8.18 Migration impact

This is a new additive subsystem. Existing Scrap, Lead, enrichment, export, billing, and crawler schemas remain authoritative and unchanged unless a later CTO-approved delta changes them.

No existing user, Lead, Scrap, or research data may be deleted or rewritten for the initial Senders implementation.

### 8.19 Implementation gate

This Senders delta is CTO-approved.

### 8.20 SMTP self-signed certificate compatibility

For SMTP sender accounts, a per-sender compatibility option `allow_self_signed_certificate` may be explicitly enabled by the user when the SMTP server presents a self-signed TLS certificate.

Rules:
1. Default is `false`; normal certificate verification remains mandatory by default.
2. When explicitly enabled, certificate verification is disabled only for that sender's SMTP TLS connection.
3. The option must never affect other sender accounts or unrelated HTTPS/TLS connections.
4. The UI must clearly identify the setting as a security exception.
5. SMTP connection tests and outbound SMTP sends must use the same per-sender TLS policy.
6. Existing sender records without the option are treated as `false`.
7. No global environment flag may be introduced to disable SMTP certificate verification.

Before coding, inspect the existing database initialization/migration mechanism, authentication/session implementation, frontend navigation structure, and deployment environment.

Implementation must be checked against this section and the inherited V1.3/V1.3.1 source-of-truth hierarchy.

No remote Git push or merge is authorized by this approval. Changes remain local unless the CTO explicitly commands otherwise.

### Cross-source enrichment identity rule
Paid Enrichment is explicitly a cross-source research operation. The selected Lead's `source_url` is provenance only and MUST NOT be used as an identity requirement, exclusion rule, or same-person match condition during enrichment. Firecrawl Search/Scrape is expected to discover other websites and independent evidence about the person.

Enrichment identity resolution MUST use person attributes/evidence such as normalized email, phone, name+company, or name+geography where supported. A different source URL is not evidence that the candidate is a different person. The original source URL MUST be preserved as provenance, while newly discovered source URLs/evidence are attached to the Lead.

The implementation MUST NOT fall back to source-URL equality merely because an enrichment source differs.
Independent-source requirement: Paid Enrichment MUST prioritize sources outside the selected Lead's original source domain. The original source URL is provenance, not an enrichment target. Same-domain results alone do not constitute cross-source enrichment. If no independent external source can be discovered/retrieved, the system must not claim a Lead was enriched or manufacture a correction/new Lead from the original source metadata alone.


Paid Enrichment is charged only when an enrichment provider is actually called. The initial wallet debit may reserve the execution charge, but if the job terminates before any Firecrawl/GPT enrichment provider call occurs, the reserved amount is credited back automatically. Once an enrichment provider call has occurred, the charge is final: cancellation, provider failure, partial completion, or later job failure does not generate a refund or credit.

## 10. Approved V1.3.1 Delta — Structured Paid Enrichment Query Planning

**Status:** CTO-approved architecture, 2026-09-25.

### Problem

Paid Enrichment currently derives Firecrawl queries by simple field concatenation. This does not explicitly distinguish the evidence objective, does not adapt search intent to missing Lead fields, and can produce search results unsuitable for the enrichment objective.

### Decision

Paid Enrichment MUST use a structured, field-aware query planner before calling Firecrawl Search.

The planner MUST construct bounded search intents from the Lead's available identity, role, company, location, and contact fields. Initial query intents are:

1. **Identity confirmation** — identify the person and distinguish similarly named people.
2. **Professional/company discovery** — establish the person's role and company relationship.
3. **Contact/source discovery** — seek missing or independently verifiable contact information and useful external evidence.

The planner MUST adapt the query set to the Lead's existing fields rather than emitting the same query pattern for every Lead.

### Email-aware source policy

- When the selected Lead already has an email, LinkedIn is an allowed enrichment source and may provide identity, role, company, or corroborating evidence.
- When the selected Lead has no email, LinkedIn MUST NOT be treated as sufficient evidence for recovering the missing email.
- When email is missing, search MUST prioritize independent non-LinkedIn sources capable of supplying or validating the email.
- When email is missing, LinkedIn may still support identity or role confirmation, but LinkedIn-only evidence does not satisfy the missing-email enrichment objective.
- The selected Lead's original source domain remains provenance and is not itself independent enrichment evidence.

### Required source handling

Search results MUST be filtered against the source policy before page retrieval and evidence classification. Same-domain results alone MUST NOT be represented as independent cross-source enrichment.

The system MUST preserve the original Lead source URL while attaching newly retrieved source URLs/evidence. A candidate MUST NOT inherit the original source URL merely because no independent source URL was supplied by the research output.

### Acceptance criteria

1. Firecrawl receives structured, bounded queries with an explicit enrichment intent.
2. Query generation changes based on whether email is present or missing.
3. Email-present Leads may use LinkedIn as enrichment evidence.
4. Email-missing Leads cannot satisfy missing-email enrichment using LinkedIn alone.
5. Independent non-LinkedIn sources are prioritized when email is missing.
6. Original source provenance is preserved and is not counted as independent enrichment evidence.
7. Query intent, source filtering, selected sources, and retrieval outcomes are available in job telemetry for audit.
8. No GPT-OSS correction or new Lead claim may be based solely on an original-source result when no independent enrichment evidence was retrieved.

### Scope

Affected components: Paid Enrichment query planning, Firecrawl Search source filtering/ranking, evidence classification, GPT-OSS candidate provenance, and enrichment job telemetry.

No change is made to SERP acquisition, Scrapy crawling, normal Lead acceptance, qualification, deduplication, or the Paid Enrichment billing policy.

## 11. Approved V1.3.1 Delta — Paid Enrichment Discovery Control and Email-Only Leads

**Status:** CTO-approved architecture, 2026-09-25.

Paid Enrichment MUST expose an explicit `discover_new_leads` control. It MUST default to `false`.

When `discover_new_leads=false`, Paid Enrichment may enrich/correct only the selected Leads and MUST NOT persist unrelated newly discovered candidates.

When `discover_new_leads=true`, a newly discovered candidate MAY be accepted as a Lead when it contains a valid personal email, even if no other person field is available. A valid personal email is a complete Lead acceptance path and may be enriched later.

Generic/role mailbox addresses MUST NOT qualify as email-only Leads. Existing authoritative personal-email qualification rules remain unchanged.

Candidate discovery MUST NOT convert every email encountered on a source page into a Lead indiscriminately. Candidates must still pass the existing extraction, personal-email validation, qualification, and deduplication pipeline. A normalized personal email is a valid identity key for deduplication.

Enrichment telemetry MUST distinguish selected Leads enriched from genuinely persisted new Leads discovered during the operation. UI wording MUST NOT imply that every extracted contact is a resulting Lead.

## 12. Approved V1.3.1 Delta — Enrichment Identity Resolution and Telemetry

Paid Enrichment MUST classify retrieved candidates against the selected Lead before merge or discovery. Identity states are `MATCH`, `POSSIBLE/UNKNOWN`, and `SAME_NAME_DIFFERENT_PERSON` at the decision layer. Name-only matching is prohibited. Existing company/geography or exact email/phone identity evidence may establish a match. Conflicting company/geography for the same name must be treated as a different person unless stronger identity evidence resolves the conflict.

A candidate without a personal email may become a new Lead only when it is identity-correlated to the selected Lead. A candidate with a valid personal email may qualify as a new Lead through the approved email-only path, subject to existing personal-email validation and deduplication.

Paid Enrichment telemetry MUST distinguish: selected Leads processed, selected Leads whose fields actually changed, fields changed, genuinely persisted new Leads, retrieved pages, and provider usage. Candidate extraction counts MUST NOT be presented as resulting Lead counts.

## 13. Approved V1.3.1 Delta — Protected Lead Fields

**Status:** CTO-approved architecture, 2026-09-26.

Any Lead field explicitly marked with * is an **automation-protected field**.

### Decision

- Scrapy/SERP extraction MUST NOT populate or replace a protected field.
- Paid Enrichment/Firecrawl/GPT-OSS MUST NOT populate or replace a protected field.
- Discovery of a new Lead MUST strip protected fields before persistence; if the remaining data no longer satisfies Lead acceptance, the candidate MUST NOT be persisted.
- Existing Lead values in protected fields MUST remain unchanged during automated processing.
- Evidence may still contain a protected field value; evidence collection does not authorize persistence of that value into the protected Lead field.
- Manual Lead Workstation editing remains allowed.
- The protection rule MUST be enforced at the persistence boundary so individual extraction engines cannot bypass it.

The authoritative implementation list is PROTECTED_LEAD_FIELDS in src/models/lead.py. The UI renders * from that same list; no field may be treated as protected solely because a frontend label was changed.

### Acceptance criteria

1. A protected field is visibly marked * in the Lead Workstation.
2. Automated enrichment cannot fill or correct the protected field.
3. Automated scraping cannot fill or correct the protected field.
4. Existing protected values survive automated processing unchanged.
5. New candidates cannot persist protected-field values.
6. Manual Workstation edits remain functional.
7. The persistence boundary enforces the rule independently of individual extraction engines.
8. Source evidence remains preservable even when its value is blocked from Lead persistence.
