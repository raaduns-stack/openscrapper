# Claw Scrapper — Source of Truth V1.2

**Status:** Canonical engineering specification.

## 1. Product definition

Claw Scrapper is an autonomous lead-research and web-extraction system.

The user provides natural-language or structured criteria, for example:
`Gold mining companies in Nigeria`.

The system must:
1. Understand search criteria.
2. Expand criteria into useful search queries.
3. Search the public internet for candidate URLs.
4. Determine which sources are worth crawling.
5. Use Scrapy/HTTP for high-volume collection.
6. Use scrapy-playwright when JavaScript rendering is required.
7. Preserve evidence/content from collected pages.
8. Use deterministic extraction first.
9. Use an LLM for research/interpretation where necessary.
10. Use OpenClaw when actual browser interaction/research is required.
11. Qualify extracted leads against user criteria.
12. Validate final data with Pydantic.
13. Self-correct failed extraction within bounded limits.
14. Deduplicate leads.
15. Export structured results.

CRM synchronization is out of scope for the V1.2 MVP.

## 2. Canonical pipeline

```text
USER -> SearchCriteria -> QueryExpander -> Discovery/Search
     -> Candidate URLs -> Relevance -> Scrapy/HTTP
     -> scrapy-playwright when required -> Evidence/Content
     -> Deterministic Extraction -> LLM Research when needed
     -> OpenClaw when browser interaction is required
     -> Qualification -> Pydantic -> bounded Self-Correction
     -> Dedupe -> Export
```

For the current V1.2 product workflow, browser-based SERP discovery is the primary discovery input. The browser extension captures Google/Bing SERP candidates and source URLs. Scrapy does not perform search discovery; it crawls URLs already captured by the extension or supplied by the enrichment workflow.

## 3. Discovery

Required components are SearchCriteria, QueryExpander, Geography, DiscoveryController,
DiscoveryAgent, SearchAggregator, search providers, and RelevanceScorer.

The MVP search provider is replaceable. Paid search APIs may be added later without
changing the rest of the pipeline.

Discovery decides **what** to crawl. For the current product workflow, the browser extension's
captured SERP URLs are the primary discovery input for research. When Start Research is
clicked, all captured SERP URLs are submitted to Scrapy for controlled enrichment.

Scrapy decides **how** to collect those URLs efficiently. It may follow internal links only
within explicit crawl boundaries: maximum depth, pages/URLs, time, allowed domains, and
relevant-link policy. The default crawl depth is safe and must not permit unbounded
recursive crawling. Controlled deeper crawling remains supported when configured.

## 4. Collection

Scrapy/HTTP is the primary high-volume collector and must provide request scheduling,
concurrency, retries, redirects, response handling, crawl state, and domain handling.

scrapy-playwright is used when ordinary HTTP cannot expose meaningful content, including
JavaScript-rendered directories, dynamic results, Load More, and client-side pagination.

## 5. Evidence and extraction

Evidence is the collected website material before interpretation. It must preserve what
the website actually says and must be distinguishable from LLM inference.

Extraction is deterministic-first:

```text
JSON-LD -> Schema.org -> structured HTML -> metadata -> email -> phone -> page text -> LLM
```

Trafilatura, metadata parsing, phonenumbers, email-validator, and Pydantic are intended
to handle cheap/reliable work before LLM interpretation.

The LLM is proportional to ambiguity, not lead count. It handles ambiguous structures,
entity identification, joining information across page content, person/business
relationships, extraction rules that cannot be made reliable deterministically, and
research decisions. It must not manufacture missing information.

## 6. Browser escalation

OpenClaw is not the primary crawler. It is the browser-interaction/research tool.

Escalation order:
1. Scrapy/HTTP.
2. scrapy-playwright if JavaScript rendering is sufficient.
3. OpenClaw if actual browser interaction remains necessary.

OpenClaw must remain behind an adapter; application code must not depend directly on
OpenClaw CLI commands. The browser adapter exposes operations such as navigate,
snapshot, click, evaluate, current_url, text, and html.

## 7. Autonomous/ReAct controller

The controller follows:

```text
Observe -> Evaluate -> Choose action -> Execute -> Observe again
```

It must maintain page limits, URL limits, duplicate detection, result-state detection,
stopping conditions, and failure handling to prevent infinite crawling.

## 8. Lead schema and evidence-based acceptance

```text
Lead
├── first_name
├── last_name
├── position
├── company_name
├── country
├── city
├── state
├── email
├── phone
├── website
└── source_url
```

A personal email is **not mandatory** for an accepted individual lead. The exact acceptance contract is:

```text
(first_name OR last_name)
AND
at least ONE of:
position, company_name, phone, city, state, country, website
```

SERP and Scrapy use this same qualification contract. There is no special SERP-only email
exception. Email remains an extraction and identity signal when present, but its absence
does not reject an otherwise valid person lead. If email is present, it must be personal.

Email-only, company-only, and name-only records are not accepted as individual leads. Supporting evidence must be a real person-specific field; extraction artifacts such as email-list/database titles, email addresses misclassified as positions, or URL/domain fragments are not valid supporting evidence.

## 9. Canonical lead lifecycle

```text
SERP candidate
    -> qualification
    -> persistent lead
    -> controlled enrichment
    -> update existing lead
       OR discover another qualifying person
    -> same qualification
    -> same dedupe/persistence path
```

The browser extension provides SERP candidates and their source URLs. When Start Research
is invoked, all captured SERP URLs are submitted to the enrichment pipeline. Scrapy may
create additional leads when controlled enrichment encounters qualifying people.

## 9. Validation and self-correction

Every final lead must conform to the Pydantic schema. Invalid structured data must not
reach export.

Self-correction is bounded:

```text
LLM -> Pydantic -> INVALID -> correction -> LLM -> Pydantic
```

There must be a hard retry limit; infinite validation/LLM loops are prohibited.

## 10. Qualification and dedupe

Qualification determines whether an extracted lead matches the user's requirements.
Extraction alone does not make a lead useful. Qualification is evidence-based and does
not require a personal email.

Deduplication occurs after extraction and qualification through one authoritative
persistence/merge path. The current implemented identity signals are normalized email,
phone, source URL plus person name, and person name plus company. Email is one identity
signal, not the sole deduplication key. Website/domain, city, and state are enrichment
fields and are not currently standalone identity keys.

All lead creation and updates, whether originating from SERP capture, batch Scrapy
research, or manual enrichment, must use this same persistence/merge path.

## 11. Exports and product surface

V1.2 target exports:
- CSV
- Excel
- Google Sheets

The CLI is a development/testing interface, not the final customer-facing product.
The eventual customer flow must allow search criteria to be defined through the UI/API.
CRM synchronization is outside MVP scope.

## 12. Production credential safety

Production credentials are immutable configuration. During diagnosis, deployment, or recovery:

- Use only the existing credentials from `/etc/claw-scrapper/claw-scrapper.env`.
- Never rotate, reset, guess, replace, or overwrite production credentials unless the CTO explicitly authorizes credential rotation.
- Never create a second credential source of truth through systemd overrides, shell profiles, code, or ad-hoc configuration.
- Read-only diagnosis must be performed before any production configuration change.
- Database authentication recovery must restore the existing configured credential, not invent a replacement.
- Temporary overrides, if explicitly authorized for emergency recovery, must be removed before the incident is closed.

## 13. Deployment safety

Production service restarts require a configuration preflight before restart:

```text
existing environment -> database connectivity test -> application startup -> health check -> stable service -> UI verification
```

A failed database connectivity check must stop deployment/restart rather than leaving the API in a restart loop. Credentials must never be modified as part of a normal deployment.
