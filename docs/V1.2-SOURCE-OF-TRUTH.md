# Claw Scrapper — Source of Truth V1.2

**Status:** Canonical engineering specification.

## 1. Product definition

Claw Scrapper is an autonomous lead-research and web-extraction system.

The user provides natural-language or structured criteria, for example:
`Gold mining companies in Nigeria`.

The system must:
1. Understand search criteria.
2. Expand criteria into useful search queries.
3. Search the public internet for candidate URLs.
4. Determine which sources are worth crawling.
5. Use Scrapy/HTTP for high-volume collection.
6. Use scrapy-playwright when JavaScript rendering is required.
7. Preserve evidence/content from collected pages.
8. Use deterministic extraction first.
9. Use an LLM for research/interpretation where necessary.
10. Use OpenClaw when actual browser interaction/research is required.
11. Qualify extracted leads against user criteria.
12. Validate final data with Pydantic.
13. Self-correct failed extraction within bounded limits.
14. Deduplicate leads.
15. Export structured results.

CRM synchronization is out of scope for the V1.2 MVP.

## 2. Canonical pipeline

```text
USER -> SearchCriteria -> QueryExpander -> Discovery/Search
     -> Candidate URLs -> Relevance -> Scrapy/HTTP
     -> scrapy-playwright when required -> Evidence/Content
     -> Deterministic Extraction -> LLM Research when needed
     -> OpenClaw when browser interaction is required
     -> Qualification -> Pydantic -> bounded Self-Correction
     -> Dedupe -> Export
```

Discovery searches the internet and produces URLs. Scrapy does not search Google; it
crawls URLs already discovered by the Discovery layer.

## 3. Discovery

Required components are SearchCriteria, QueryExpander, Geography, DiscoveryController,
DiscoveryAgent, SearchAggregator, search providers, and RelevanceScorer.

The MVP search provider is replaceable. Paid search APIs may be added later without
changing the rest of the pipeline.

Discovery decides **what** to crawl. Scrapy decides **how** to collect it efficiently.

## 4. Collection

Scrapy/HTTP is the primary high-volume collector and must provide request scheduling,
concurrency, retries, redirects, response handling, crawl state, and domain handling.

scrapy-playwright is used when ordinary HTTP cannot expose meaningful content, including
JavaScript-rendered directories, dynamic results, Load More, and client-side pagination.

## 5. Evidence and extraction

Evidence is the collected website material before interpretation. It must preserve what
the website actually says and must be distinguishable from LLM inference.

Extraction is deterministic-first:

```text
JSON-LD -> Schema.org -> structured HTML -> metadata -> email -> phone -> page text -> LLM
```

Trafilatura, metadata parsing, phonenumbers, email-validator, and Pydantic are intended
to handle cheap/reliable work before LLM interpretation.

The LLM is proportional to ambiguity, not lead count. It handles ambiguous structures,
entity identification, joining information across page content, person/business
relationships, extraction rules that cannot be made reliable deterministically, and
research decisions. It must not manufacture missing information.

## 6. Browser escalation

OpenClaw is not the primary crawler. It is the browser-interaction/research tool.

Escalation order:
1. Scrapy/HTTP.
2. scrapy-playwright if JavaScript rendering is sufficient.
3. OpenClaw if actual browser interaction remains necessary.

OpenClaw must remain behind an adapter; application code must not depend directly on
OpenClaw CLI commands. The browser adapter exposes operations such as navigate,
snapshot, click, evaluate, current_url, text, and html.

## 7. Autonomous/ReAct controller

The controller follows:

```text
Observe -> Evaluate -> Choose action -> Execute -> Observe again
```

It must maintain page limits, URL limits, duplicate detection, result-state detection,
stopping conditions, and failure handling to prevent infinite crawling.

## 8. Lead schema and acceptance

```text
Lead
├── first_name
├── last_name
├── position
├── company_name
├── country
├── city
├── state
├── email
├── phone
├── website
└── source_url
```

Accepted individual lead:

```text
(first_name OR last_name) AND email
```

All listed fields are desired, but only the above rule is mandatory for acceptance.
Email-only and company-only records are not accepted as individual leads.

## 9. Validation and self-correction

Every final lead must conform to the Pydantic schema. Invalid structured data must not
reach export.

Self-correction is bounded:

```text
LLM -> Pydantic -> INVALID -> correction -> LLM -> Pydantic
```

There must be a hard retry limit; infinite validation/LLM loops are prohibited.

## 10. Qualification and dedupe

Qualification determines whether an extracted lead matches the user's requirements.
Extraction alone does not make a lead useful.

Deduplication occurs after extraction and qualification. Signals may include normalized
business name, phone, website/domain, city, and state, with stronger identifiers taking
precedence. The accepted individual-lead contract remains authoritative.

## 11. Exports and product surface

V1.2 target exports:
- CSV
- Excel
- Google Sheets

The CLI is a development/testing interface, not the final customer-facing product.
The eventual customer flow must allow search criteria to be defined through the UI/API.
CRM synchronization is outside MVP scope.
